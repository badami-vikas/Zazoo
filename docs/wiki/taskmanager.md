# Task Manager Module

Full depth: [../raw/taskmanager-module-plan-2026-07.md](../raw/taskmanager-module-plan-2026-07.md) · BRD: [../raw/brd-taskmanager-2026-07.md](../raw/brd-taskmanager-2026-07.md). Status: **DONE** 2026-07-21 (TASK-021, AP-066). Bridge PR #41 + Corporate PR #104. Signed `task-manager@1.0.2`. External two-instance PASS. Zero blockers.

## Core call

One installable Module. Owns **single execution queue** per workspace. Agent-first: coding agent often primary queue consumer, not human. Productizes proven system — repo's own `docs/TASKS.md` + Task Manager UI (AP-024/025) + user's game-designs repo converged on same format independently. Queue = governed Database; `tasks.md` file = **projection, never second store**.

## Layers — REVISED TWICE (2026-07-16, 2026-07-17 — both user pushback, both correct)

**ONE type.** 2026-07-16: dropped Initiative/Outcome as types (Initiative stays retired per AP-020; Outcome folds to a field). 2026-07-17: dropped Goal as a type TOO, after the user asked "why does Goal need to exist separately — a root task already branches" and demanded full tree-surgery flexibility (insert new ancestor above an existing branch: `b.c.d`→`a.b.c.d`; promote a branch to a new root dropping a stale ancestor: `b.c.d`→`c.d`, keeping `c`'s identity). A hard-typed Goal would force a TYPE MIGRATION on every promote/demote — exactly the friction the user wanted gone.

- **Task** (canonical) — the ONLY type. Self-referential, materialized dot-path id (`2.3.5`), `status: candidate` = old Initiative meaning, `outcomes[]` = old Outcome, **`is_goal: boolean`** = old Goal. The flag travels with the row through any re-parenting — restructuring is always a pure `parent_task_id`/`path` update, never a table migration. Demoted former-root still reads as a reviewed anchor wherever it now sits ("sub-goal" falls out free). Promoted branch keeps its own `is_goal` value untouched unless a Human flips it.
- Execution layer (Task→Action→Evidence→Verification) = existing pipeline, reused not rebuilt.
- Not a "universal entity table" (already-rejected Taskade pattern): ONE domain, ONE Database, self-referential — same as the already-blessed Touchpoint tree, just leveled + flagged.

## Load-bearing rules

- One queue. Bugs/decisions/requests = evidence attached to tasks, never queues (prevents: ~100 lost bugs).
- Every Task: dot-path id + outcomes[] + **exit test** (fastest honest disprove-test) before in-progress — UNLESS `is_goal=true`, which may run on `review_cadence` instead (goals aren't expected to hit one terminal "done").
- Status is NOT one-directional: done/archived/parked can be **reopened** to pending/in_progress (normal task-manager convention), typically on a changed outcome target — `target-change-reopen-prompt` Automation.
- Intake = reconcile first (search same outcome, attach, don't add). Duplicate-merge = proposal only.
- Every Task/Goal create triggers Internal Strategist impact-fit-analysis → resequence proposal, before it settles into queue.
- **Tree restructuring is governed**: promote (drop ancestor, subtree becomes root) / insert-ancestor-above (wrap in new parent) / re-parent — all proposals, path recomputed atomically over the affected subtree only (never partial).
- **Routing — REVISED 2026-07-17 (ADR-107)**: NO default executor. Chief of Staff (not Internal Strategist) owns `agent-task-routing` — matches required Skill against eligible Agents (reuses the real shipped `SkillManifest` resolution, ADR-104). Ambiguous/no-match → escalates to explicit Human assignment, never guesses. Why CoS: routing = dispatch/coordination, CoS's existing glossary-defined role + shipped @mention-dispatch precedent; Internal Strategist keeps impact-fit + restructuring (placement/strategy questions, not "who executes").
- **Reschedule + routing governance share one mechanism**: human proposals need approval every time at first. Confidence-calibration (reuses VAR-1/Variance-Adjuster) tunes off vetted human approve/veto history; once calibrated, MINOR/unambiguous cases auto-apply via a deterministic system gate (reuses ADR-073 `classifyApprovalBand` — kernel decides, agent explains, agent-floor DENY untouched). Significant/ambiguous always need approval.
- Proactive value: Internal Strategist scheduled scan across installed-Module data → proposes new value-adding Tasks as candidate drafts, never silent writes.
- Read budget: hot head (in-progress + next few) ≤ ~2k tokens; completed bay capped (10/7d) → archive, swept by Automation not memory.
- Agent writes = pipeline drafts, approve|edit|veto. No CRDT, no universal-entity table.

## Capabilities

- Agents: NO new permanent. **Chief of Staff = agent-task routing owner (2026-07-17)**; Internal Strategist = planning brain + impact-fit + tree-restructure + proactive scan; Learning = intake evidence + calibration signal (now for BOTH reschedule and routing); Governance = explains guards; Capability Builder = one eligible executor among several, never a default.
- Skills (15): goal-outcome-framing · candidate-task-generation · premortem-scenario · task-decomposition · **task-tree-restructure (NEW)** · exit-test-authoring · task-reconciliation · queue-sequencing · impact-fit-analysis · agent-task-routing (owner: CoS, no default) · reschedule-confidence-calibration (shared reschedule+routing) · proactive-opportunity-scan · ledger-projection · evidence-verification · progress-synthesis · habit-scaffolding.
- Playbooks v1 capped 5 (`outcome-key-results`, `backward-planning`, `clarify-organize`, `measurable-review`, `pre-mortem`) = versioned configs, not 20 skills. **REAL since 2026-08-08 (ADR-197)** — each now carries methodology, intent, the technique's questions, system-prompt guidance, and which Skills it may run. Ids stay technique-named, never book-brand-named; no protected text copied. `TASK_MANAGER_PLAYBOOKS` is derived from that content, so roster and content cannot drift.
- **TM3 gap closed in three slices, 2026-08-08.** Found by auditing the shipped Module against its own plan: all 18 `task-manager.*` Skill ids were registered manifests whose `run()` ECHOED inputs — externally indistinguishable from working Skills, which is why it survived certification. Slice 1 (ADR-196): reconciliation + queue-sequencing + impact-fit, deterministic, no model — they run on every create and decide placement. Slice 2 (ADR-197): the four generative Skills, model-backed on the **Local Plane only** (router fails rather than falling through to cloud), with the Playbook's questions + zero drafted items + a stated reason as the honest offline answer. Model never authors dot-paths, statuses, or ids. Slice 3 (ADR-198): the last ten, and **the echo fallback became a THROW** — a registered id with no implementation now fails loudly, since that fallback is exactly what let TM3 ship declared-but-not-built. Four had no logic anywhere (`task-execution.ts`); five had tested core implementations never bound to a Skill id; `exit-test-authoring` joined the Playbook Skills under existing `measurable-review` (no 6th Playbook — v1 cap of 5 holds). **Skill catalog: 18/18 execute, none echoes.**
- **Automations built, 2026-08-08 (ADR-198)**: `planning-playbook` (NEW, human-triggered — these Skills answer a question someone asked, so the trigger is a person; the Automation exists to give it an attributable Run) and `proactive-scan-cadence` (declared since TM0 with no runtime id). Procedures `taskManager.runPlanningPlaybook` / `runOpportunityScan`; both attributable Internal Strategist Runs halting at `pending_review`. Manifest `1.1.0`→`1.2.0`. **`standup-brief` deliberately NOT bound**: Chief of Staff-owned, and CoS has no governed runtime Agent identity — binding it to Internal Strategist would make it run by discarding ADR-107's ownership split. Nine other declared Automations still unbound.
- **Approval MATERIALIZES since 2026-08-08 (ADR-199)** — the third step of draft-then-approve. One pure `task-materialize.ts` called by both `decideProposal` implementations (no migration: `TaskProposalKind` already had `candidate`, `kind` is `text`). Pipeline proposal + Task-Manager row share one id, so one human decision resolves both. Approve a decomposition → child Tasks appear as **`candidate`** (worth having, not "start these"); paths are **recomputed** against the current queue, never taken from the payload; an approved pre-mortem writes **nothing** on purpose; outcomes never arrive as north star; scan candidates land under the Task their own finding named; generated Tasks are owned by the **approver**, never the drafting Agent. Model call is now governed via an optional `RunCtx.modelProvider` → real ledger receipt; **plane still local — governance is not consent**. - **Approval is EDITABLE since 2026-08-08 (ADR-200)** — the third decision. `candidate` joins `projection_reconcile` as an editable kind, so one bad child title no longer costs an eight-child decomposition. The edit is an allow-list **MERGE** over the ONE content key the STAGED kind materializes from; `kind`, run id, model receipt and Playbook questions carry over verbatim, and `kind` is absent from the wire schema entirely because it picks which materializer branch runs. Three validation layers (`.strict()` schema → merge against the kind → per-entry at materialize), because a Human's edited text is exactly as untrusted as a model's. **Two refusals:** an edit materializing nothing is rejected (an approval that writes nothing is a veto in disguise); a pre-mortem refuses an edit (approving one writes nothing by design). Agent's draft preserved on the row as `agentDraft`. `archive_sweep`/restructure stay approve-or-veto — computed plans over specific rows/versions, staleness-checked at decision time. Also closed: `taskManager.proposal` read query (an edit surface needs a read surface) and planning Runs now finish with the decision, not just "a draft was produced". **Not yet**: no UI reaches the edit — `TaskManagerPage` shows approve/veto for `impact_fit` only.
- **Chief of Staff is a real Agent since 2026-08-08 (ADR-201)** — it had no governed runtime identity, so all four Automations ADR-107 put under it were undeclarable-in-practice: an Automation starts an Agent Run, only an attributable Agent invokes a Skill, so **an owner that cannot act owns nothing that can run**. Scope is narrow — no `record:archive` (CoS coordinates and reports, Governance archives) — and exactly one allow-listed Skill. `standup-brief` + `stale-task-review` now run via `taskManager.runQueueBrief`; both **REPORT and stop** (no proposal, action `read`, no proposed status — approving a report is theatre). One Skill behind both: `progress-synthesis`'s `stalled` list IS staleness over a longer window, so no 19th Skill. `evaluateTaskGuards` gains `stale_task` sharing `isStalenessEligible` with it (`candidate`/`parked` are SUPPOSED to sit still; `blocked` is not) and skips rather than guesses with no clock. Manifest `1.2.0`→`1.3.0`. **Still unbound**: `agent-task-routing-on-assign` (belongs with the routing gate) and `dependency-unblock-notifier` (needs absent schema Relations).
- **Guard + gate Automations run since 2026-08-08 (ADR-202)** — `wip-breach-detector`, `unverified-done-challenger`, `reschedule-approval-gate`, `routing-approval-gate`. All four were declared since TM0 with nothing to run: `evaluateTaskGuards`/`classifyTaskChangeBand`/`calibratedTaskChangeDecision` were core code with **no Skill id**. New Governance Skills `queue-guard` + `change-gate` (18→20). **The gate now calibrates on REAL ledger history** — `approvalBand` took approve/veto counts as CLIENT inputs, so a caller could hand itself a calibrated verdict; the gate counts rows matching `skill === "task-manager.change-gate"` + change kind. Each Automation reports only its own finding kind. Both Skills declare `record:read` alone — the first run was REJECTED (Governance has no `record:write`) and the fix was narrowing the Skills, not widening the Agent. Recorded: `unverified-done-challenger` is unreachable via `transition` (the store refuses `done` without verification) — it covers rows arriving by projection reconcile. Manifest `1.3.0`→`1.4.0`.
- **Internal Strategist's four Automations bound, 2026-08-08 (ADR-203)** — `task-created-impact-analysis`, `task-tree-restructure-proposal`, `target-change-reopen-prompt`, `goal-review-cadence`. Three already halted for review, so the gap was **attribution, not governance**: the proposal's actor was the HUMAN who triggered it with `KERNEL_PASSTHROUGH_SKILL`, so the rule "every Task create triggers Internal Strategist impact-fit-analysis" named an Agent that was a string label on a row. A moved target IS an impact-fit question (no new Skill). `goal-review-cadence` stays IS-owned despite `queue-guard` being Governance's — planning question, not control question. Manifest `1.4.0`→`1.5.0`. **Still unbound**: `agent-task-routing-on-assign` (needs a routing surface applying the gate) and `dependency-unblock-notifier` (needs absent schema Relations).
