## What shipped

Two Tools, each a registry entry plus a panel, per the Module's existing
"a Tool is an entry plus a panel" contract.

### 1. Tags and Internal Notes (`whatsapp.tool.annotations`)

Bridge's own data about a chat, Person, or Community. Touches no WhatsApp
surface at all — it makes no engine call, so it works outside the desktop shell.

- `platform/modules/whatsapp/src/annotations.ts` — pure reducers over a
  `LocalStateStore` JSON namespace (`whatsapp:annotations`). No clock, no RNG,
  no I/O; ids and timestamps are caller-supplied, matching `messages.ts`.
- Tags are case-folded and whitespace-collapsed on both write **and** read, so
  "Investor"/"investor" can never resurface as two tags from older stored state.
- A subject carrying neither tags nor notes is pruned, so "how many things have
  I annotated" stays true.
- The persisted-state reader is **salvaging**, not all-or-nothing: one malformed
  subject or note is skipped and the rest survives. Deliberately different from
  `readSyncState`, which discards everything — losing a cursor costs a re-read,
  losing these would destroy the owner's own writing.
- Note authorship is taken from the authenticated identity in the router, never
  from client input.

### 2. Analytics and Audit Log (`whatsapp.tool.audit`)

- `platform/modules/whatsapp/src/audit.ts` — append-only log in namespace
  `whatsapp:audit`, capped at 2,000 events.
- **Built only from Bridge's own actions.** No engagement metrics, no per-contact
  message counts, nothing read from the account. There is no backfill because
  there would be nothing honest to backfill from.
- `auditEventFromOutcome` maps an `OutboundOutcome` from the real outbound gate
  into a row. The analytics are therefore the send path's own decisions written
  down, not a parallel counter that could drift from them.
- Retention drops the **oldest** and counts what it dropped; `dropped` is
  reported next to `total` so "0 refusals" can be distinguished from "refusals
  that retention already discarded".
- `AuditDetail` is restricted to scalars, and the reader strips anything else —
  a message body structurally cannot end up in an audit row.
- Appending a duplicate id is a no-op, so a retried action cannot double-count.

### Wiring

- `platform/apps/api/src/router.ts` — `annotations`, `addTags`, `removeTag`,
  `addNote`, `removeNote`, `auditLog`, `recordSendOutcome`. Audit rows are now
  written by the two existing paths that actually do something:
  `stageExtraction` and `ingestMessages`. `recordWhatsAppAudit` deliberately
  never throws into its caller — a sync must not be rolled back because its
  bookkeeping failed.

### The send-recording gap, stated plainly

`engine.ts` already wires `performAutomatedSend` → the Rust ceiling, but
`sendAutomatedMessage` currently **has no callers**. Bridge has therefore
attempted zero sends, and the send counters are genuinely zero rather than
under-reporting.

Two things follow, and both are handled rather than left implicit:

1. `recordSendOutcome` was added as the seam. It is explicitly **not** a send
   procedure — it records an outcome the gate already decided, and touches no
   transport, so it cannot become a second write path to WhatsApp. When the send
   call site is built, recording is one line. It rebuilds the outcome shape and
   defers to `auditEventFromOutcome`, so rows come from the mapping the Module
   tests cover rather than a second hand-written one.
2. The panel does **not** render five zero tiles when nothing has been recorded.
   "Refused: 0" reads as "no send was refused", which is a different and
   stronger claim than "no send has been recorded at all". It shows the latter.

The one-line call at the send site belongs to whoever owns `engine.ts` /
`ChatsSurface.tsx` — files this agent was instructed not to touch.
- `platform/apps/web/src/app/pages/whatsapp/AnnotationsPanel.tsx`,
  `AuditLogPanel.tsx`, dispatched from `WhatsAppPage.tsx` on `tool.id`.
- `platform/modules/manifests/src/index.ts` — two capabilities. Neither declares
  any WhatsApp read permission, because neither Tool performs one.

## Constraint compliance

- **No new write path to WhatsApp.** Neither Tool sends. `audit.ts` only *reads*
  `OutboundOutcome` as a type; the ordered gate (policy refusals → `decideSend`
  → Rust ceiling) is untouched.
- **Local Plane only.** Both namespaces are `LocalStateStore`. No dual-write, no
  promote path.
- **Honest empty states.** Annotations: "Nothing to annotate yet — sync a chat
  first." Audit: "Bridge has not recorded any activity in this window", and if
  retention discarded rows it says so instead of implying nothing happened. No
  sample or placeholder row exists in either panel.
- **No decorative controls.** Every control performs a governed action against a
  real procedure.
- **`docs/dummy.md`:** no entry needed — this change introduces no dummy or
  sample data. The `check:no-dummy-runtime` guard passes.
