## 2. The real cause: two honesty defects compounding

Neither is in Rust's security boundary. The boundary held throughout; `list_chats` reaches the page
correctly (the `script_for_message_op` delegation is present and verified).

### 2a. `list_chats` read one field and called it three

`platform/apps/desktop/src-tauri/src/whatsapp_message_ops.rs`

```js
var last = c.lastReceivedKey ? c.t : c.t;   // both arms identical
```

An unfinished expression. It only ever read `c.t`, and on the live account `c.t` is absent — so all
500 chats came back with `lastMessageTimestamp: null`.

A second, latent defect in the same script: `c.id.isGroup()` was called unconditionally. On builds
where `isGroup` is a plain boolean the call throws, is swallowed by the surrounding `catch`, and
**every group silently looks like a direct chat**. Not the reported bug, but the same class, in the
same five lines, so it is fixed here.

### 2b. The scheduler treated "I cannot tell" as "nothing new"

`platform/modules/whatsapp/src/messages.ts` (`chatsDueForSync`) and its copy in the web
`sync.ts` loop:

```ts
if (typeof activity !== "number" || !Number.isFinite(activity) || activity <= 0) return false;
```

With all 500 chats undated, `due` was empty, `queue.length === 0`, and that rendered as:

> Everything is already up to date.

**The success message is what hid the total read failure.** That is the honesty defect from the
brief, and it is also why this bug survived long enough to be reported by a human rather than a test.

### Why all three strings appeared at once

They were three separate subsystems each telling a partial truth: the session had 500 chats, the
store had none, and the sync could not bridge them but said it had.

## 3. What changed

**`whatsapp_message_ops.rs`** — timestamp extraction now consults `c.t`, `c.lastMsgTimestamp` and
`c.msgs.last().t`, and reports **`null`, not `0`**, when none answers, so "unknown" survives the trip
to the scheduler. `isGroup` is handled as either property or method. Only numbers are read; the
no-message-bodies guarantee is unchanged and still asserted.

**`whatsapp_webview.rs`** — Defect 3. `health_script()` now builds from a merged, **de-duplicated**
list of `WPP_DEPENDENCIES` + `MESSAGE_WPP_DEPENDENCIES`, so `WPP.chat.getMessages` is checked at
**link time** rather than at first sync. It is existence-checked only and never invoked — calling it
in a tripwire would read a real conversation at session start. The dead-constant compiler warning is
gone.

**`messages.ts`** — `chatsDueForSync`: an undated chat is due for **exactly one** read, gated on the
store's cursor. Unbounded re-reads against a personal number is the behaviour that draws enforcement
(ADR-158), so convergence is not optional. New `chatsWithoutActivityTime` helper so a surface can
state the fact instead of inferring currency from an empty queue.

**`sync.ts`** — the same scheduling fix on the live path, plus split reporting: `nothing-readable`
is a distinct status from `completed`, and both the "session listed no chats" and "nothing could be
dated" cases report the **failed** phase. Outcomes carry `chatsListed` and
`chatsWithoutActivityTime`.

**`ChatsSurface.tsx`** — the failed phase renders in the danger colour, not as quiet grey progress
text. The empty chat list stops telling the user to run a sync that has already run and failed. The
status bar now **labels its planes**: `500 chats on WhatsApp · nothing stored in Bridge yet`. The
session is authoritative about WhatsApp, the store about Bridge; unlabelled, two true facts read as a
contradiction. That is the coherence fix the brief asked for.

### A test that asserted the bug

`messages.test.ts` contained `"chats are due only when activity is strictly newer than their
cursor"`, which asserted that a chat with **no timestamp is never due**. That is the defect written
down as a requirement. I rescoped it to dated chats and moved the undated cases into new tests.
Flagging it explicitly because silently deleting an assertion is how a fix becomes a regression.

## 5. What still needs a live run — precise procedure

**Everything above is verified by build and test only. None of it has been demonstrated against your
live session.** Two things need you at the keyboard.

### Test A — does the fix actually sync? (the exit test)

1. Rebuild the desktop shell so the new Rust `list_chats` is in the binary. A web-only reload is
   **not** enough — the script lives in Rust.
2. On the Chats surface, confirm the status bar now reads something like
   `Session live — 500 chats on WhatsApp · nothing stored in Bridge yet`.
3. Press **Sync messages**.

Expected: the run schedules chats instead of returning instantly. Three possible results, all of
them now honest:

- **Chats start syncing** and `M stored in Bridge` climbs — fixed.
- **Red banner**: "None of the 500 chats reported a last-activity time…" — the scheduler fix worked,
  the timestamp extraction still does not. Not a regression; it is the failure finally being visible.
  Send me the number.
- **Red banner**: "The WhatsApp session reported no chats at all" — a different problem, and it can
  no longer masquerade as success.

The one outcome that should now be impossible is a silent "Everything is already up to date" over an
empty store.

### Test B — which timestamp field actually answers?

I could not determine this without your live store, and the fix deliberately does not depend on it —
undated chats are read regardless. But sync is cheaper when chats can be dated, so it is worth
knowing. In the WhatsApp session webview's console:

```js
(() => {
  const c = WPP.whatsapp.ChatStore.getModelsArray();
  const has = (f) => c.filter(f).length;
  return {
    total: c.length,
    t:               has(x => typeof x.t === "number" && x.t > 0),
    lastMsgTimestamp:has(x => typeof x.lastMsgTimestamp === "number" && x.lastMsgTimestamp > 0),
    msgsLastT:       has(x => { try { const m = x.msgs?.last?.(); return typeof m?.t === "number" && m.t > 0; } catch { return false; } }),
    sampleKeys: Object.keys(c[0] ?? {}).filter(k => /^(t|.*[Tt]ime.*|.*[Tt]imestamp)$/.test(k)),
  };
})()
```

This reads counts and property names only — **no message text**. `sampleKeys` is the useful part if
all three counts are zero: it names whatever the current bundle actually calls the field, and I can
add it to the extraction list.
